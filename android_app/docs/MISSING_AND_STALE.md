## Server interaction (sync) — shipped 2026-11-15

Android now talks to `zakken_server` over a websocket. The wire lives in Rust behind uniffi (`zakken_server/client_internals/server_link/`, wrapping `shared_internals` which is shared with web); the Kotlin business logic lives in `z/zndroid/sync/owner_of_interacting_with_server/` and mirrors web's `cqrs_state_synchronization/web_interface/src/owner_of_interacting_with_server/` one file per file.

Works end-to-end (first run against a live server, 2026-11-15): connect, login, receive queued letters, apply them, ack them. Verified on a real phone: 50+ queued letters drained and applied, no duplicate pushes after ack.

Exists but not yet exercised: send path (Android edit → server), two-client visibility (Android edit → web, web edit → Android), drift/reconcile flow end-to-end, `wipe_dataset` end-to-end, `TheDriftVersionChanged` push handling.

Now exists: recovery UI (`MainPages/RecoveryPage.kt` + `sync/.../Recovery.kt`). Reconcile UI (server-wins on conflict). Wipe-self-and-adopt-server. Debug-only wipe-server on the recovery screen. `NavPage` conn-status banner (shows only on Lonewolf / LonewolfAndOffline, with a "Fix" button to `RecoveryPage`; not shown when Connected, so the recovery screen is unreachable from a healthy client — that's a known gap). `menuTick` observer on `NavPage`. ViewPage remote-edit merge via `editor/OpenPageRegistry.kt` (a letter for an open page merges into the live doc rather than being deferred).

The old "## Android has no server interaction" section below is historical. It describes what was missing before 2026-11-15 and should not be read as current state.

## Still open after 2026-11-15

A failed `PageBatcher` batch is dropped and the page reloads. This is the intended failure strategy: reload from DB is Android's replacement for web's `APP_LOCKED`, and the drain happens before the write so the retry path doesn't loop. Edits pushed during the failed write stay queued and are flushed by `destroyAfterFlush` before the boss is destroyed. The one loss is the batch that failed to write — that's the reload's job to make visible.




`SchemaVersion`'s V0/V1/V2 `updateOnce` steps still swallow exceptions.



Positional column reads remain in `SchemaVersion.V0` (frozen, fine).

The e2e external transaction has no savepoint, so a failing block under e2e leaves its earlier writes in the transaction until teardown. Cannot be fixed in Kotlin: `LiveForever` (z_db) exposes `beginAllOrNothing` / `everythingWentPerfectly` / `regretEverything` only, no `savepoint` / `releaseSavepoint` / `rollbackTo`. Adding savepoint support is Rust-side work in z_db, out of scope for the Android-only session. Documented as a known limitation of the e2e harness.



## Android has no server interaction (HISTORICAL, superseded 2026-11-15)

Superseded by "Server interaction (sync) — shipped 2026-11-15" above. Kept for the pre-sync state.

Before 2026-11-15, Android was local-only. Nothing synced. The one function that exists to trigger a send is a do-nothing stub:

    // z/zndroid/actions/Kick.kt
    fun kickSend() {
        // future: notify the sender that client_love_letter has new rows
    }

Every committed write already calls it (actions, PageBatcher flush), so the wiring site exists. Nothing calls a server. What a working sync needs, roughly in dependency order:

- A socket layer. Reference: `cqrs_state_synchronization/web_interface/src/owner_of_interacting_with_server/` and `zakken_server/client_internals/shared_internals/`.
- Login/register handshake. Same reference.
- A send loop that drains `client_love_letter` rows and posts them as love letters. Reference: web's `send_unsent_love_letters_to_server_if_there_are_any.rs`.
- A receive loop that pulls unsent letters and applies them to the local docs. Reference: web's `main_for_receiving_spontaneous_love_letters_from_server.rs` and `main_for_applying_love_letter_from_server_to_app.rs`.
- Sync mode and the gate every sync-touching path reads. Reference: web's `sync_mode.rs`, template's `shared_owners/client_status.rs`. Connection states on web include `Lonewolf` and `LonewolfAndOffline` (spelled that way in Rust).
- Drift version handling. Every message sent to the server carries the client's current drift version, taken from a stored value that only the recovery verbs update. The server refuses any request whose version doesn't match; register, login and GetCurrentDrift are exempt because they are how a client learns the version. Login's reply carries the current version, the reason it changed, and an optional solution picked by whoever caused the drift (wipe-and-adopt-server, reconcile, or absent meaning the user picks). On mismatch at login the client transitions to lonewolf.
- Every spontaneous love letter from the server carries the drift version the server is on. The client checks it against its own and throws the letter away on mismatch.
- A server push saying the drift version changed, sent just before the server closes the socket. On receipt the client reconnects and re-logs-in, which is where it learns the new version.
- Reconcile and the other data-management verbs (wipe server, adopt). Reference: web's `owner_of_sync_state_and_recovery/`, template's same. Reconcile exists on web as a full flow (`cqrs_state_synchronization/web_interface/src/leptos_components/reconcile_page/`) using four wire requests: `GetPageFingerprints`, `GetPagesByIds`, `GetReconcileVersion`, `ReconcileLetters`. Fingerprint is SHA-256 of the page blob, computed by `drift_guard_shared::fingerprint`. Reconcile uses a separate `reconcile_version` counter so two reconcilers can't both succeed off the same snapshot. See `ZakkeN/nov11.md` and `ZakkeN/zakken_server/guide_to_interacting_with_server.md`.
- Reconcile does NOT drain the outbox (`ZakkeN/nov12claude.md`). It fingerprints local pages against the server's (block texts only), shows one card per differing page (client-only pages get no card), sends ONE `ReconcileLetters` batch, then wipes the client locally and pulls the server dataset. Android's `client_love_letter` queue semantics should be designed with that in mind.
- A client-status derivation for the page title and any UI state that depends on connectivity.
- Manifest and backup prerequisites (read 11-13). `AndroidManifest.xml` has no `INTERNET` permission, so the socket layer needs `<uses-permission android:name="android.permission.INTERNET" />` first. It also has `allowBackup="true"`; Both XML files were read 11-13 and are the unedited template: `data_extraction_rules.xml` has an empty `<cloud-backup>` (no include or exclude) and no `<device-transfer>` section, so Android backs up and restores everything under the app's data directory, `my_database.db` included, and `backup_rules.xml` (`fullBackupContent`, which only API 30 and older read) is unused at `minSdk` 31. A restore happens on new-phone setup or a Play reinstall, not on `adb install -r`. A restore onto a second phone would then carry over the first phone's `user_id`, session counter and unsent `client_love_letter` rows. Decide this before sync lands, for example by excluding the database in `data_extraction_rules.xml` (it governs on Android 12+, and `minSdk` is 31).

None of that exists. When the first piece lands, several items below become "obviously follow from this", so start at the top.

## Bugs in the code

Historical record from 2026-11-13. Many entries below were fixed on 2026-11-15 (see the "2026-11-15 session: fixed" summary above). Only entries re-verified since then are current; the rest are kept so history isn't lost. Re-verify against the code before acting on any entry.

- Under the e2e external transaction (`externalTransactionActive`), `withTransaction` never enters the log-buffer path and the routing element's `logBuffer` is never used. Logs written during a test go straight to the DB and are rolled back with the rest at teardown.
- The `logs` table is nearly empty in practice (11-13 grep of `app/src`). The only callers of `Logger.i` / `Logger.e` are in `ViewPageLogs`, and `ViewPage` calls three of its five helpers (`logPageInit`, `logPageLoadSuccess`, `logPageLoadError`), so each page open writes two rows. `logBossInstanceError` and `logDocEventError` have no caller, and `Logger.w` has none. Save failures, migrations, actions and the batcher log nothing (they use popups). Either log from those paths or stop describing the table as a record of failures.
- `Storage/StorageAccess.getUserId` returns `""` when the key is missing, with no error and no log. An empty user id would be written into every yrs doc created afterwards. `StorageInitializer` normally prevents it.
- FIXED 2026-11-19: `EditableBlock.kt` & `PageSession.kt`: `onValueChange` routes any text containing `\n` or `\r` to `PageSession.onMultiLineInput`, which splits normalized lines into blocks while preserving prefix/suffix text and cursor offset; `PageSession.computeDiff` uses a sound code-point prefix/suffix differ; `onPreviewKeyEvent` consumes `Shift+Enter` and guards `Enter`/`Backspace`/`DirectionUp`/`DirectionDown` on `selection.collapsed`.
- `executor/Operations.kt::insertPageRequiresThreeDbInserts` does four inserts (page row, title block, body block, love letter). The name is stale.
- FIXED 2026-11-19: `EditableBlock.kt::BlockActionMenu` now sets `canMoveDown = !isTitle && index < session.rows.size - 1`, so the title's Down button is disabled.
- Focus and scroll: the scroll to a focused row is `listState.animateScrollToItem(index)` inside each block's own `LaunchedEffect`; `ViewPage` has no page-level effect (older docs said it did). The effect only exists for a composed block, so a new row that lands below the visible area may not be composed, and then neither the scroll nor the focus happens until the user scrolls.
- External transaction mode (`DbManager.externalTransactionActive`): `withTransaction` runs the block inside the open transaction and has no savepoint. A block that throws returns a failure, but its earlier writes stay in the transaction until teardown. In production the same failure rolls back. So the e2e run never exercises the rollback path, and a failed batch under e2e leaves half-applied rows. `LiveForever` (z_db) exposes no `savepoint` / `releaseSavepoint` / `rollbackTo`, so fixing this is Rust-side work in z_db.
- FIXED 2026-11-19: `ViewPage.kt` `onDispose` calls `OpenPageRegistry.unregisterAndClose(session)` (which runs `PageSession.destroyAfterFlushAsync()` and tracks the `Job` per `pageId`), and `ViewPage`'s load `LaunchedEffect` calls `OpenPageRegistry.awaitPendingClose(pageId)` before reading the DB.
- `actions/PageActions.renamePage` always sends `Replace`, so the known non-ASCII `Delete`/`Replace` miscount in yrs (`SHARED_MEMORY.md`) applies to it: renaming a page whose current title contains å/ä/ö or emoji probably ends in "Rename failed: rename readback mismatch" and a rolled-back transaction, not a rename (the readback check stops it corrupting data). Creating such a page is unaffected (insert at 0). Typed edits that produce Delete/Replace diffs in text with such characters are exposed too, and the Kotlin block-edit path has no readback. From reading; not run; the Rust side not checked.
- `actions/PageActions.kt::createNewPage` then runs `editBlockRequiresThreeDbInserts` on the fresh boss, so a new page emits two love letters (CreateNewPage and EditBlock). Web emits one. Not a bug; noted for a future alignment pass.
- `actions/MoveBlock.kt::moveBlockToAnotherPage`: fixed 2026-11-19 — flushes any registered `OpenPageRegistry` sessions for source and target pages before taking `WriteLock` (unregistered sessions such as `OpsChecks` scratch sessions still flush explicitly).
- `editor/PageBatcher` creates its own `CoroutineScope(Dispatchers.IO + SupervisorJob())` that is never cancelled. One per opened page; harmless in size but never released.
- `editor/PageBatcher.closeAndFlush` is `flushNow` and closes nothing, so the name is wrong. Rename it `flush`, or give the batcher a real close that cancels the scope and refuses later pushes.
- `editor/PageBatcher` failure path: the batch is drained from the queue before the write, so a failed batch is dropped and the page reloads from the DB. Edits pushed to the old batcher after that drain stay queued there, and its debounce can fire later against the destroyed boss. That would show a second "Save failed" popup and call `onFailed` again, bumping the shared `reloadToken` and reloading the new session. From reading only; not run. Cancel the old batcher's scope when the session is replaced.
- `editor/PageBatcher.runOneFlush` calls `GlobalPopupManager.showError` (suspend, unbuffered flow) while holding `flushMutex`, and calls `onFailed()` only after it returns. `showError` returns at once when nobody is collecting (the flow drops the value, see the `GlobalPopup.kt` entry), so recovery still runs, only without the popup. (An earlier version of this entry said recovery would hang and later flushes would wait on the mutex; that was wrong.)
- `editor/PageBatcher.debounceJob`: fixed 2026-11-19 — all reads/writes are guarded by `synchronized(debounceLock)`, and `armDebounce` cancels only the delay coroutine while running the flush in its own coroutine.
- `db/migrations/SchemaVersion`: every `updateOnce` step swallows its exceptions, and `MigrationManager` records the new version regardless.
  - V0 wraps `copyTable` and `dropTable` of `uncommitted_diffs` in one try/catch, so a failed copy skips the drop and nothing is destroyed (an earlier version of this list said it dropped anyway; that was wrong).
  - V1's repair wraps its copy/create the same way, so a failed repair is written to `key_value_storage` as success.
  - V0 also drops and recreates `key_value_storage` and copies rows back only if the read succeeded. A failed read is swallowed to null and every stored row is lost, `user_id` included. Whether `XEqualY("1", "1")` returns all rows depends on z_db and was not checked.

The nav menu is built from the mirror (`Reads.getMenuPages`), so on a device that has data every existing page disappears from the menu while its blob and outbox rows stay, and `MirrorVsYrsCheck` flags every page. Accepted as pre-data (see `OUTSIDE_ANDROID_APP.md`); a rebuild-mirror-from-blobs step would make it safe.

## Different shape from web, not necessarily wrong

Called out so nobody "fixes" them into breaking:

- `PageBatcher` on Android is one class with its own debounce timer, mutex and queue. Web has a `BatcherHandle` plus a run-loop task.
- `DbManager` uses `DbTransactionElement` in the coroutine context for re-entrancy. Web uses `WriteLock` + `run_exclusive`.
- Android batches Delete and Move in the same queue as Edit and Add (see `INVENTED_ON_ANDROID.md`).

## 2026-11-25 CM6 editor: bugs found on device, not fixed

Two device-run bugs after the CM6 port. Documented here, not chased. Both are new (no web equivalent), so they're not imported web bugs.

### "save failed couldn't remove 3 items from an array" during fast split or merge

Reproducer: type a few chars, then Enter in the middle of the block, or Backspace at position 0, quickly — before the 500 ms batcher debounce has flushed. `PageBatcher.writeBatch` fails, popup shows `Save failed: ...`, page reloads.

Likely cause, from reading (not confirmed): `combineGetdiffResults` in `text_diff` composes a chain like `[Insert("def", 3), Delete("def", 3)]` on a block that is being deleted in the same batch. If the composition produces `Delete("def", 3)` without the prior insert being honoured, `yrs` tries to remove 3 items at position 3 in a shorter text and throws. The `combineGetdiffResults` composition of adjacent insert-then-delete at the same positions is the suspect; a stray native yrs array mutate is the observed effect.

Not confirmed because:
- The batch is drained before the write (see `PageBatcher.runOneFlush`), so the failed batch is lost and the page reloads.

How to investigate (for a future AI with zero context):
1. Locate every `combineGetdiffResults` call: `grep -rn "combineGetdiffResults" /home/zakke/ProgStuff/ZakkeN/android_app/app/src/main/java/z/zndroid`. Only `PageBatcher.writeBatch` calls it today. The copy in `text_diff` Rust is the algorithm source.
2. Add a temporary log inside `PageBatcher.writeBatch` right before `combineGetdiffResults`: print `blockId` and each `DiffResult` variant in that block's run, in order. Reproduce the crash, read the logcat with `adb logcat -s PageBatcher:V`. The sequence that precedes the exception is the one to reason about.
3. Build a headless reproducer: a `DevCheck` that does `session.onInput(idx, TextFieldValue("abc"))` then `session.onEnter(idx, 1)` in immediate succession, then forces `session.flush()`. If that throws inside `combineGetdiffResults` / `yrs`, the bug is in the batcher or the diff composition, not in CM6. If it passes, CM6 is producing diffs the headless path doesn't; compare the two.
4. The stale-flag interplay to watch for: `PageBatcher` squashes edits across entries by grouping with `groupBy` on `blockId`, then `combineGetdiffResults` on each group. A `Delete` composition that assumes a prior `Insert` was applied cannot safely cross a structural op that has already been flushed. If the sequence within a run is `Insert("def", 3)` then `Delete("def", 3)` at the same position without an intervening state change, the combined diff should collapse to `NoDiff`, not to `Delete("def", 3)`. Anything that emits the latter against a text shorter than 3+3 chars is the bug.

### Caret jumps to wrong location for a split second after a split

Reproducer: press Enter in the middle of a block, watch the caret. It lands at the split point briefly, then snaps to its final position.

Likely cause, from reading: `pendingFocus` sets the selection on Main via `Cm.setSelection` + `Cm.focusKeepCaret`. `EditableBlock` also calls `webView.requestFocus()` (added 2026-11-25, in the `LaunchedEffect(session.pendingFocus.value)`). `requestFocus()` on a WebView does its own caret placement (usually position 0 or last-known), which briefly overrides the CM selection until `Cm.setSelection` lands. The one-frame flash is between the two.

Not chased. Fix likely means calling `Cm.setSelection` first, then `requestFocus`, or skipping `requestFocus` when CM already has DOM focus (`cm.isReady` + a JS-side "is focused" check).
