# Missing and stale — Android

Living list, started 2026-10-31. When something here gets fixed, delete the entry or mark it done. When something new is found, add it.

Not every entry is equally important. The first section is the big one; the rest are smaller.

## Android has no server interaction

Today Android is local-only. Nothing syncs. The one function that exists to trigger a send is a do-nothing stub:

    // z/zndroid/actions/Kick.kt
    fun kickSend() {
        // future: notify the sender that client_love_letter has new rows
    }

Nothing calls a server. The full list of what a working sync would need, in roughly the order it depends on itself:

- A socket layer. Reference: `cqrs_state_synchronization/web_interface/src/owner_of_interacting_with_server/` and `zakken_server/client_internals/shared_internals_for_server/`.
- Login/register handshake. Same reference.
- A send loop that drains `client_love_letter` rows and posts them as love letters. Reference: web's `send_unsent_love_letters_to_server_if_there_are_any.rs`.
- A receive loop that pulls unsent letters and applies them to the local docs. Reference: web's `main_for_receiving_spontaneous_love_letters_from_server.rs` and `main_for_applying_love_letter_from_server_to_app.rs`.
- Sync mode (`Connected` / `NeedsReconcile`, with the seven reasons) and the gate every sync-touching path reads. Reference: web's `sync_mode.rs`, template's `shared_owners/client_status.rs`.
- Dataset-generation check on login, and the lonewolf transition when it changes.
- Reconcile and the other data-management verbs (pause, wipe server, adopt). Reference: web's `owner_of_sync_state_and_recovery/`, template's same.
- A client-status derivation for the page title and any UI state that depends on connectivity.

None of that exists. When the first piece lands, several below become "obviously follow from this", so start at the top.

## Stale code

- `DbManager.addPage` and `DbManager.renamePage` are marked deprecated and forward to `z.zndroid.actions.createNewPage` / `renamePage`. Either remove them or finish the migration. Right now there are two entry points for the same action.
- `DbManager.activeTransactionThreadLocal` is set by `withTransaction` and read by `Logger.log` to decide whether to buffer a log entry in the transaction's `logBuffer` or write it directly. But `withTransaction` is `suspend`, and a coroutine that suspends inside the block can resume on a different thread. When that happens, `Logger.log` reads `null` from the ThreadLocal and writes the log to the DB via a fresh coroutine — which then blocks on `DbManager`'s mutex until the transaction commits. So the log ends up written *after* the transaction, not buffered and dropped with it, and not rolled back with it. The intended behaviour (buffer if inside a transaction) works only for non-suspending code. Fix: use the `DbTransactionElement` that already lives in the coroutine context. `Logger.log` isn't `suspend`, so either make it `suspend` or read the transaction state from a place that survives thread changes.
- `ThreadUtils.io` is a one-line alias for `doInBackground`. Same function, two names. Pick one.
- `z/zndroid/DocEvents/` is an empty folder. `AI_READ_THIS.md` correctly says "There is no DocEvents package any more". Remove the folder.
- `Storage/FastStorageKey.kt` — both `RefreshCondition` and `DropCondition` are documented as placeholders for future logic. `CURRENT_DOCUMENT` is one of only two keys in the enum. Confirm `FastStorage` is actually populated; if nothing reads these keys, the file is dead.

## Different shape from web, not necessarily wrong

These are called out so a future reader doesn't "fix" them into breaking:

- `PageBatcher` on Android is a single class that owns its own debounce timer, mutex and queue. On web the equivalent is a `BatcherHandle` that talks to a run loop task via a channel, and the run loop owns the pending list. Same external behaviour, different internal shape. Aligning would mean adding a handle + task split on Android, which is a bigger change than the code currently needs.
- `DbManager` uses a coroutine-context element (`DbTransactionElement`) for transaction re-entrancy. Web uses `WriteLock` + `run_exclusive`. Same effect.

## Added after reading ViewPage / EditableBlock / NavPage / NewPagePopup (2026-10-31, third pass)

- `MainPages/NavPage.kt` has a helper at the bottom: `private fun MenuPageRow.titleText(): String = title`. It's used exactly once (inside the delete dialog) and its body is a field access. Delete it and use `currentInfo.title` directly. The naming suggests "text of the title" but it returns the field, so it adds nothing.
- `MainPages/ViewPage/EditableBlock.kt::onPreviewKeyEvent` — `Key.Enter` with shift returns `false` (does not consume), so shift+enter falls through to `BasicTextField`'s default handler, which inserts a newline, which then hits `onValueChange`'s `contains('\n')` branch that calls `onEnter` anyway. Behaviour is "shift+enter behaves like enter", which is probably wrong; shift+enter should insert a soft newline or do nothing. If it's meant to be a no-op, the `if (!event.isShiftPressed)` check plus returning `false` doesn't achieve that — it accidentally routes the newline into a split. Either drop the shift check (accept that shift+enter splits) or intercept the newline in `onValueChange` (whatever the intended behaviour is, put it in one place).
- `MainPages/ViewPage/EditableBlock.kt::onPreviewKeyEvent` — for both `Key.Enter` and `Key.Backspace`, only `selection.start` is read. If the user has a range selected and presses backspace, the range isn't cleared — the split/merge runs on the selection endpoint, ignoring that a range was selected. BasicTextField would normally delete the range; intercepting before it can means multi-char selections behave wrong. Either check that `selection.collapsed` before acting, or let the default handler run when a range is selected.
- `MainPages/ViewPage/EditableBlock.kt` — the software keyboard's newline is handled in `onValueChange` by `contains('\n')`, but that fires whenever the text *contains* a newline, not when one was just inserted. Pasting multiline text into a block deletes every newline silently and calls `onEnter` once at the paste-end cursor. Pasted text that spans lines gets mangled. Either split on every newline at paste-time, or reject multiline pastes in the field.
- `MainPages/ViewPage/ViewPage.kt` — three separate `session?.closeAndFlush()` call sites (BackHandler, top-bar back button, lifecycle ON_STOP) plus a `closeAndFlushAsync()` in `onDispose`. ON_STOP and onDispose fire on every back-out and every app-background, so the batcher gets flushed 2–3 times per leave. Idempotent because the queue is empty after the first, but the extra work is noise. Fold the four call sites into one `leavePage()` local function.
- `MainPages/ViewPage/ViewPage.kt` — `StorageAccess.setValue(StorageKey.CURRENT_DOCUMENT, pageId)` sets the "currently open document" key on every page-load effect, and never clears it on leave. If a component reads it after leaving, it sees a stale pageId. Either clear on leave, or drop the key entirely (nothing in the app appears to read it — verify).
- `MainPages/ViewPage/EditableBlock.kt::BlockActionMenu` has "H1" and "Todo" buttons that do nothing (`onClick = { }`). They exist in the UI and do not work. Either implement or remove — right now tapping does nothing visible and looks like a bug.
- `MainPages/ViewPage/AdminViewOfPage.kt` — this whole file is dev-facing (compares SQLite vs CRDT, copies content for manual recovery). It's reachable in release because `MainActivity` routes to it unconditionally (no `BuildConfig.DEBUG` check at the route site). DevTools is gated; AdminView is not. Gate the route.
- `MainPages/ViewPage/ViewPage.kt` — on load, if `newSession.rows.isEmpty()` it shows an error but leaves the `session` variable null. If the user then presses back, `session?.closeAndFlush()` is a no-op and the page is left with no flush. That's fine — nothing to flush — but the reload button does not exist: the popup says "Reload to try recovery" and there's no reload affordance on-screen. The user has to back out and re-open. Either add a reload button or change the popup wording.

## Added after reading actions, WriteLock, SessionManager, TableDescriptors, SafeRowMapper (2026-10-31, fourth pass)

- `docs/AI_READ_THIS.md` describes the `logs` table as having `details` and `details_type` columns, and `new_log_row` as taking eight arguments. The live code does neither: `Version1.logsColumns()` (the frozen snapshot the schema test compares against) has no `details` / `details_type`, `LogsTableSchema` matches that, `DbManager.writeLogEntry` calls `newLogRow` with six arguments, and `LogEntry` carries `details` / `details_type` fields that nothing consumes. The data model was simplified but the doc wasn't updated. Fix `AI_READ_THIS.md`'s logs paragraph. Also decide whether to delete the two dead `LogEntry` fields or wire them up.
- `db/schema/TableDescriptors.kt` — `BacklinksTableSchema` and `IncomingLoveLettersTableSchema` declare `Col.Blob` for what `AI_READ_THIS.md` describes as `disabled` (nothing specific) and `love_letter` (nothing specific). The `backlinks.disabled` descriptor expects `Blob`; if the real column is TEXT, every read throws `ClassCastException` at runtime rather than at boot. Confirm against `client_table_blueprints`.
- `Storage/SessionManager.kt::incrementAndStore` fires on a background coroutine and swallows exceptions to a popup. `MainActivity` calls it on every navigation change (`navController.addOnDestinationChangedListener`). So every navigation bumps the session id and writes to the DB. `INVENTED_ON_ANDROID.md` documents this as wrong ("`MainActivity` no longer increments on every navigation change") — but the code still does it. The `addOnDestinationChangedListener` block in `MainActivity.onCreate` needs to be deleted.
- `Storage/SessionManager.kt::initialize` reads the stored value, sets `_currentSessionId` to it, then immediately calls `incrementAndStore()`. So on app start the session id goes from `N` to `N+1` before `initialize` returns to `MainApplication`. That's probably what's intended (fresh process = new session), but the comment says "Initial increment for app startup" — the flow relies on `incrementAndStore` awaiting `readyDeferred`, which was completed one line earlier. The `_currentSessionId.set(stored)` followed by `incrementAndGet` is equivalent to setting `stored + 1` directly; the two-step is harder to read than it needs to be.
- `protocol/SafeRowMapper.kt` — `mapRow` has `skipId = true` by default, so callers who forget to think about it skip the `id` column automatically. `StorageInitializer` passes `skipId = true` explicitly. `DbManager.writeLogEntry` passes neither (defaults to true). The three call sites are consistent by accident, not by design. If a future `new_*_row()` ever returned a row that *did* include `id` (e.g. an insert with an explicit id), one caller would blow up. Consider making `skipId` a required parameter or a `enum class RowShape { WithId, WithoutId }` argument so every call site names its intent.
- `WriteLock.kt` — the file has only one consumer type: every action and the batcher. But the doc in `SHARED_MEMORY.md` and the code comment both say "Nothing inside a locked section may try to take WriteLock again." That's a real constraint and the Kotlin `Mutex` doesn't enforce it (it just deadlocks). Web has the same issue (`run_exclusive` is not re-entrant). Nothing to fix — just a note that this is a shared footgun, not a bug.
- `actions/PageActions.kt::createNewPage` — `insertPageRequiresThreeDbInserts(pageCtx)` inserts the page row, title block, body block, *and* a client_love_letter row. Then `editBlockRequiresThreeDbInserts(editCtx)` runs on the fresh boss and inserts *another* client_love_letter row. So creating a page with a name emits two love letters — CreateNewPage and EditBlock — back to back. Web's `create_page` emits exactly one letter (`CreateNewPage` with a title-bearing snapshot). Both are valid; Android's is two round-trips where web's is one. Not a bug; note it so a future alignment pass knows about it.
- `actions/MoveBlock.kt::moveBlockToAnotherPage` — takes `oldBoss` and `newBoss` as arguments and assumes the caller has already established that neither has queued writes. But `PageBatcher` holds the queue, not the `BossOfYrs`, so "the boss has queued writes" is never literally true. What the caller actually has to guarantee is "the *page's* batcher is flushed". The doc comment is misleading. Either accept a `PageSession`/batcher handle instead of a boss and flush inside, or say "caller must have flushed both pages' batchers" explicitly. Right now it says "neither boss has queued writes" which can't be checked and doesn't name the real requirement.

## Added after reading logging, migrations, storage (2026-10-31, sixth pass)

- `log/LogDateHelpers.kt::toUnixRange` / `toUnix` return Unix *seconds* (`LocalDateTime.toEpochSecond`), but `LogEntry.timestamp` is set with `System.currentTimeMillis()` which is *milliseconds*. Any range query against the `logs.timestamp` column that uses these helpers is off by a factor of 1000. Nothing currently uses them (ViewPageLogs doesn't build range queries), so it's not an observed bug — but the helpers and the writer disagree and the next person to write a date range query will hit it. Either make the helpers return ms or make `LogEntry.timestamp` seconds.
- `log/Logger.kt` — `logScope.launch { DbManager.writeLogEntry(entry) }`. Fire-and-forget coroutine, no error handling. If the write fails (DB not ready, transaction open elsewhere, etc.), the exception is swallowed by `CoroutineScope.launch` (default handler just prints to stderr). The log is on Logcat but not in the DB and nobody knows. Either add a `CoroutineExceptionHandler` or `try/catch` around the launch body.
- `log/Logger.kt` — `Logger.e` builds `fullMessage = "$message | Error: ${throwable.message}\n${Log.getStackTraceString(throwable)}"` and puts the whole thing in `message`. The `details` / `details_type` params exist and would be the natural home for the stack trace, but the `logs` table has no columns for them (see correction above). Stack traces in `message` means a long error eats a whole column. Not urgent.
- `Storage/StorageAccess.kt::rummage_in_storage` — reads the value column via `row.cols.lastOrNull()`. This is a positional assumption on the `key_value_storage` schema, in the one file whose own reads elsewhere are descriptor-based. `TableDescriptors.kt` already has `KeyValueStorageTableSchema.value` — use it.
- `Storage/StorageAccess.kt::setValue` — memory-first ordering bug. It writes to `FastStorage` before entering the transaction. If the DB write fails (transaction rollback, exception thrown), the memory cache still holds the new value while the DB holds the old one (or nothing). The next `rummage_in_storage` returns the new value. On process death the value is lost. Do the DB write first; only `FastStorage.set` after the transaction succeeds.
- `Storage/StorageAccess.kt::setValue` — inside the transaction it calls `rummage_in_storage(key)`. `rummage_in_storage` reads `FastStorage` first. Because the memory cache was just set, the "current" lookup always returns `StringValue` even on a first insert. That means `setValue` always takes the "edit existing row" branch for FastStorage-enabled keys, even if there's no row to edit. Works today because the first write goes through `insertData` (row exists afterward), but if the first `setValue` ever rolled back, every later `setValue` would silently no-op. Fixed by the previous point (DB first).
- `Storage/StorageAccess.kt::getUserId` returns `""` when the key is missing, no error and no log. Callers pass that into `docFromSnapshot`, which happily uses an empty user_id. Every block created under that id is unattributable. `StorageInitializer` does create a fresh user_id on first run, so the failure mode requires the write to be skipped or the DB to be wiped. Either throw or log an error.
- `Storage/FastStorage.kt` has `drop` and `exists` methods, neither of which is called anywhere in the code I've read. Either they're used in files I haven't seen (lab, DbGui, tests) or they're dead. Verify; delete if unused.
- `Storage/StorageKey.kt` — the `SESSION_ID` comment says "Increments on app launches and screen changes." That's a description of the current code (`MainActivity` bumps on navigation), but `INVENTED_ON_ANDROID.md` and `SessionManager.initialize`'s comment both say it should be per process, not per navigation. The comment enshrines the bug. Update after `MainActivity`'s `addOnDestinationChangedListener` block is removed.
- `Storage/SessionManager.kt::incrementAndStore` — `_currentSessionId.incrementAndGet()` runs synchronously, but the DB write is fire-and-forget on a coroutine. A caller that reads `currentSessionId` immediately sees the new value even though the DB may not be updated. If the process dies before the write completes, next launch re-increments from the old value and could reissue a session id that was already used in `client_love_letter`. For a local app this is probably acceptable, but it's a silent collision path.
- `db/migrations/SchemaVersion.kt::V0.updateOnce` — the very first thing it does is `db.copyTable("uncommitted_diffs", "client_love_letter")` inside `try {} catch {}`, then `db.dropTable("uncommitted_diffs")` inside `try {} catch {}`. If `uncommitted_diffs` exists but `client_love_letter` also exists (from a partial prior migration), `copyTable` may throw, the catch swallows it, and `dropTable` succeeds — destroying data that was never copied. V0 is ancient history, so the odds of a real DB being in that state are low. Flagging as a landmine for anyone who ever reseeds a V0 fixture.
- `db/migrations/MigrationManager.kt::readCurrentVersion` — reads the value column via `row.cols.lastOrNull()`. Same positional assumption as `StorageAccess.rummage_in_storage`. If `key_value_storage` ever gains a column after `value`, this silently reads the wrong data.
- `db/migrations/SchemaVersion.kt::assertLatestMatchesBlueprints` — compares against `Version1.logsColumns()`, which has six non-id columns. If the live `newTableLogs()` in Rust ever grows a `details` column (as `AI_READ_THIS.md` implies it already has), the check would fail. Currently the check probably passes because the live blueprint has the same six columns as the frozen one — meaning the doc drift noted above isn't caught by any test. That's the point of the check, and it doesn't currently cover the drift.

## Added after reading components, debug receivers, dev tools (2026-10-31, seventh pass)

- `components/GlobalPopup.kt::GlobalPopupManager` — `messages` is a `MutableSharedFlow<Popup>()` with default capacity 0 and replay 0. `emit` on such a flow suspends until a subscriber is ready. `GlobalPopup()` in `MainContainer` is the only subscriber, and only after `ZndroidTheme` composes. So a `GlobalPopupManager.show(...)` call from a coroutine that runs before the popup composable starts collecting blocks that coroutine until first composition. Most call sites are inside user-triggered coroutines that run after compose, so it doesn't blow up in practice — but a "show this before the UI mounts" case will hang. Give the flow a small buffer (`MutableSharedFlow(extraBufferCapacity = 16, onBufferOverflow = BufferOverflow.DROP_OLDEST)`) or document the constraint.
- `components/GlobalPopup.kt` — `collectLatest` cancels the previous `showSnackbar(...)` when a new popup arrives. With `SnackbarDuration.Indefinite`, a rapid sequence of `showError` calls means only the last one is visible. That may be intended (don't stack errors) but it means a user who triggers two errors back-to-back will only see the second. If they need to see both, use a queue instead of `collectLatest`.
- `components/GlobalPopup.kt::GlobalPopup` — the `Snackbar` uses `containerColor = MaterialTheme.colorScheme.errorContainer` unconditionally. Info popups (`isError = false`) render with the same error-red background as actual errors. The only visual difference is the `"ERROR: "` prefix on the text. Either drop the prefix and let the colour carry the signal, or split the colours.
- `MainContainer.kt` — fine. No findings.
- `TestTransactionReceiver.kt::onReceive` (CHECK_SYNC branch) — the title-to-pageId resolution does a `WHERE content = rawPageId` on `every_block_in_existence` without an `is_title = true` filter in the query itself. The title filter is applied afterward in Kotlin by reading a column position, and `firstOrNull` means if two pages share a title, whichever row comes first in the DB (insertion order) is picked. Titles are not unique — two pages called "Untitled" are common. Either add `AND is_title = 'true'` to the WHERE clause, or accept that CHECK_SYNC's title resolution is unreliable.
- `TestTransactionReceiver.kt::onReceive` — the fallback positions `?: 1` and `?: 5` on `indexOfFirst` don't fire when `indexOfFirst` returns -1 (they only fire when the whole optional chain is null). If a schema migration ever reorders the columns, `indexOfFirst` returns the new correct index, so this is fine. If a column is renamed, `indexOfFirst` returns -1, and the next line's `getOrNull(-1)` returns null, which then falls through to `?: rawPageId`. Silent. Not a bug today; note it.
- `DbGui.kt`, `InspectTable.kt`, `SchemaGui.kt` — all three are reachable in release. `MainActivity`'s route table has `db_gui`, `schema_viewer`, `inspect_table/{tableName}` with no `BuildConfig.DEBUG` check. Only the nav button to open `DbGui` is not gated; the route itself exists in release. Same shape as the `AdminViewOfPage` finding. Gate the routes, or at minimum gate the nav buttons.
- `InspectTable.kt` — writes here bypass `WriteLock` and `DbManager.withTransaction`. `DbManager.insertData(...)` / `DbManager.deleteRow(...)` take DbManager's mutex, but not WriteLock, so a batcher flush in progress (which holds WriteLock, then DbManager mutex) can't interleave inside `executeNative`, but a write from `InspectTable` between two batcher flush steps of an action is possible if the action ever released the DB mutex. In practice the DB mutex serialises every operation, so the DB doesn't see partial state. But the "one writer at a time" rule is bypassed. Dev-only; low priority. Document, don't fix unless it's easy.
- `InspectTable.kt` — the delete button reads `row.cols.firstOrNull()` as the id, then `DeleteRowIn(tableName, idStr)`. For INTEGER id columns this passes a stringified integer into a `delete_row`, which sqlite coerces. Works today. If a future table ever has a TEXT primary key on a non-first column, it breaks. Same positional-assumption pattern as the rest.
- `InspectTable.kt` — `inputs` is a `mutableStateMapOf<String, String>()` used for row insert. It's not cleared on error. Inserting once, failing, then inserting again would carry the previous input over. Minor UX wart. Also the insert `ColumnValue(col.name, colValue)` builds the values in `columns.filter { !it.primaryKey }` order, which is `checkTable`'s returned order — consistent with `insertData`'s expectations if the DB preserves column order, but it's a hidden coupling.
- `SchemaGui.kt` — `tableSchemas` is hardcoded to five tables: `pages`, `client_love_letter`, `backlinks`, `every_block_in_existence`, `key_value_storage`. The live schema also has `logs` and `incoming_love_letters`. The viewer is incomplete. Add them, or drive the list from `DbManager.listTables()` and dispatch to the right `newTableX()` per name.
- `SchemaGui.kt` — `data class TableSchema(...)` lives in this file, used only here. Fine as long as it's only the schema viewer. If a second consumer appears, move it to `db/schema/`.
- `components/GlobalPopup.kt` — the `Snackbar` at bottom-center uses `statusBarsPadding()` AND `navigationBarsPadding()` AND `padding(16.dp)`. `SnackbarHost` inside a `Box` with `contentAlignment = BottomCenter` is fine; the combination of both system-bar paddings plus 16dp gives a fairly large gap on notched devices. Cosmetic.
