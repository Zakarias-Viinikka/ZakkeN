# Missing and stale - Android

Living list, started 2026-10-31. Re-verified against the code on 2026-11-13. Nothing is carried over unverified from 10-31 any more; where a claim rests on files that were not read, the entry says so. When something here is fixed, delete the entry. When something new is found, add it.

Sections are ordered by how likely the item is to bite.

## Android has no server interaction

Today Android is local-only. Nothing syncs. The one function that exists to trigger a send is a do-nothing stub:

    // z/zndroid/actions/Kick.kt
    fun kickSend() {
        // future: notify the sender that client_love_letter has new rows
    }

Every committed write already calls it (actions, PageBatcher flush), so the wiring site exists. Nothing calls a server. What a working sync needs, roughly in dependency order:

- A socket layer. Reference: `cqrs_state_synchronization/web_interface/src/owner_of_interacting_with_server/` and `zakken_server/client_internals/shared_internals/`.
- Login/register handshake. Same reference.
- A send loop that drains `client_love_letter` rows and posts them as love letters. Reference: web's `send_unsent_love_letters_to_server_if_there_are_any.rs`.
- A receive loop that pulls unsent letters and applies them to the local docs. Reference: web's `main_for_receiving_spontaneous_love_letters_from_server.rs` and `main_for_applying_love_letter_from_server_to_app.rs`.
- Sync mode and the gate every sync-touching path reads. Reference: web's `sync_mode.rs`, template's `shared_owners/client_status.rs`. Connection states on web include `Lonewolf` and `LonewolfAndOffline` (spelled that way in Rust).
- Drift version handling. Every message sent to the server carries the client's current drift version, taken from a stored value that only the recovery verbs update. The server refuses any request whose version doesn't match; register, login and GetCurrentDrift are exempt because they are how a client learns the version. Login's reply carries the current version, the reason it changed, and an optional solution picked by whoever caused the drift (wipe-and-adopt-server, reconcile, or absent meaning the user picks). On mismatch at login the client transitions to lonewolf.
- Every spontaneous love letter from the server carries the drift version the server is on. The client checks it against its own and throws the letter away on mismatch.
- A server push saying the drift version changed, sent just before the server closes the socket. On receipt the client reconnects and re-logs-in, which is where it learns the new version.
- Reconcile and the other data-management verbs (wipe server, adopt). Reference: web's `owner_of_sync_state_and_recovery/`, template's same. Reconcile exists on web as a full flow (`cqrs_state_synchronization/web_interface/src/leptos_components/reconcile_page/`) using four wire requests: `GetPageFingerprints`, `GetPagesByIds`, `GetReconcileVersion`, `ReconcileLetters`. Fingerprint is SHA-256 of the page blob, computed by `drift_guard_shared::fingerprint`. Reconcile uses a separate `reconcile_version` counter so two reconcilers can't both succeed off the same snapshot. See `ZakkeN/nov11.md` and `ZakkeN/zakken_server/guide_to_interacting_with_server.md`.
- Reconcile does NOT drain the outbox (`ZakkeN/nov12claude.md`). It fingerprints local pages against the server's (block texts only), shows one card per differing page (client-only pages get no card), sends ONE `ReconcileLetters` batch, then wipes the client locally and pulls the server dataset. Android's `client_love_letter` queue semantics should be designed with that in mind.
- A client-status derivation for the page title and any UI state that depends on connectivity.

None of that exists. When the first piece lands, several items below become "obviously follow from this", so start at the top.

## Bugs in the code

- **Session id still bumps on every navigation.** `MainActivity` registers `navController.addOnDestinationChangedListener { SessionManager.incrementAndStore() }`. `INVENTED_ON_ANDROID.md` and `SHARED_MEMORY.md` describe the intended per-process behaviour. Delete the listener block. `NavController` calls a newly added listener immediately with the current destination, so the id also bumps once more at every launch, and again after each activity recreation (rotation, for example) because the effect re-adds the listener. From the `NavController` contract, not run. The doc comments in `SessionManager.kt` ("or when the user navigates") and `StorageKey.SESSION_ID` ("and screen changes") also enshrine the bug; fix them at the same time.
- `SessionManager.initialize` sets the id to the stored value, then calls `incrementAndStore()`, which is fire-and-forget on its own coroutine. So `currentSessionId` is still `N` when `initialize` returns, and becomes `N+1` a moment later. (An earlier version of this list said it was `N+1` before returning; that was wrong.) Setting `stored + 1` directly and persisting it would be simpler.
- `SessionManager.incrementAndStore` does both the in-memory bump and the persist inside one fire-and-forget `scope.launch` (after `readyDeferred.await()`), so `currentSessionId` lags the call. (An earlier version of this list said the bump was synchronous; it is not.) Two quick calls can persist out of order: the writes run under `withTransaction` in lock order, not value order, so the stored value can end up lower than the in-memory one. If the process dies before the write lands, the next launch re-issues an id that may already be in `client_love_letter`.
- `SessionManager.initialize` maps `NotFound`, `Error` and an unparsable value to 0 alike. A transient read error resets the counter to 0, and the next write persists 1 over the real value, so ids already in `client_love_letter` get re-issued.
- `SessionMonotonicityTest` only checks the id is >= 1 and unchanged over 100 ms. It cannot catch the per-navigation bump, and the "still 0 on a first-ever launch" failure I inferred earlier is unlikely in practice: the check is reached through Dev Tools, and navigating there already bumps the id, so it would need the check to run within milliseconds of launch. The opposite is possible: a navigation bump landing inside the 100 ms window fails it with "changed without navigation". Neither was run.
- **Logger finds the transaction through a ThreadLocal.** `DbManager.activeTransactionThreadLocal` is set by `withTransaction` and read by `Logger.log`. `withTransaction` is suspend, so after a suspension the coroutine may resume on another thread and `Logger.log` sees `null`. It then writes the log via a fresh coroutine that blocks on `dbMutex` until the transaction ends, so the log lands after the transaction instead of being buffered and flushed on rollback. Fix: read the `DbTransactionElement` from the coroutine context (needs `Logger.log` to be suspend or take the element), or carry the state somewhere that survives thread changes. How likely this is (11-13 read of `DbManager`): inside a transaction every `executeNative` takes the context-element branch and never touches the mutex, and `withContext(txElement)` keeps the same dispatcher, so the transaction bodies read so far do not actually suspend and the thread does not change. The case that does happen is a log from another thread or coroutine while a transaction is open: it is not buffered, goes through `logScope`, waits for `dbMutex` and lands after the commit or rollback. If a switch ever did happen, `finally { activeTransactionThreadLocal.remove() }` would run on the new thread and leave the stale element on the old pool thread, where every later `Logger.log` would append to a dead `logBuffer` and be lost.
- Under the e2e external transaction (`externalTransactionActive`), `withTransaction` never sets the ThreadLocal and the routing element's `logBuffer` is never used. Logs written during a test go straight to the DB and are rolled back with the rest at teardown.
- `Logger.log` fire-and-forget: `logScope.launch { DbManager.writeLogEntry(entry) }` has no error handling. A failed write is lost silently (Logcat has the line, the DB does not). `writeLogEntry` returns a `Result` that the launch discards. Lines logged before `DbManager.init` has set `db` fail with `NotReady` and are dropped. `logScope` is `CoroutineScope(Dispatchers.IO)` with no `SupervisorJob` (`PageBatcher`'s scope has one), so an `Error` thrown in one write would cancel the scope and every later DB log would be skipped; unlikely, since `executeNative` catches `Exception`.
- `Logger.e` puts the whole stack trace in `message`. `Logger.e(details, detailsType)` and `LogEntry.details` / `detailsType` exist but are dropped, because the `logs` table has no such columns. Either delete the dead fields or add the columns through a migration.
- `log/LogDateHelpers.kt::toUnixRange` / `toUnix` return seconds. `LogEntry.timestamp` is `System.currentTimeMillis()` (milliseconds). Any range query built from the helpers is off by 1000. They also read the `LocalDateTime` as UTC, so a range picked in local time is shifted by the device's offset. Nothing uses them yet.
- `Storage/StorageAccess.setValue` writes `FastStorage` before the DB transaction. If the DB write fails, memory holds a value the DB doesn't. Inside the transaction it calls `rummage_in_storage`, which reads `FastStorage` first, so for FastStorage keys it always takes the "edit existing row" branch even on a first insert. `SESSION_ID` and `CURRENT_DOCUMENT` are both FastStorage keys and nothing else inserts them (`StorageInitializer` only inserts `user_id`, and a grep of `app/src` on 11-13 finds `SESSION_ID` only in `SessionManager`, `StorageKey` and `FastStorageKey`), so their rows are probably never created: the edit updates zero rows, or `editColInRowWhere` throws and `SessionManager` shows a "Session Error" popup on every launch. If so, the stored session id is never persisted and `initialize` starts from 0 on every launch. This depends on how z_db's `editColInRowWhere` treats a missing row and was not checked; open Database Inspector, then `key_value_storage`, and look for a `session_id` row. Fix: do the DB write first, update `FastStorage` after it succeeds, and insert when the DB row is missing.
- `Storage/StorageAccess.getUserId` returns `""` when the key is missing, with no error and no log. An empty user id would be written into every yrs doc created afterwards. `StorageInitializer` normally prevents it.
- `MainApplication.onCreate` runs `DbManager.init` in a bare `CoroutineScope(Dispatchers.IO).launch`. If init throws, the uncaught exception kills the process, and if it were caught `readyDeferred` would never complete so every `awaitReady()` would hang.
- `MainPages/ViewPage/EditableBlock.kt::onPreviewKeyEvent`:
  - Shift+Enter returns `false`, so the newline reaches `onValueChange`, whose `contains('\n')` branch calls `onEnter` anyway. Shift+Enter behaves like Enter. Decide the intended behaviour and put it in one place.
  - Enter and Backspace read only `selection.start`. With a range selected, Backspace at 0 or Enter runs the split/merge instead of deleting the range. Check `selection.collapsed` first.
  - `onValueChange` strips every `\n` and calls `onEnter` once at the cursor, so pasting multi-line text mangles it. Split per newline or reject multi-line pastes.
- `executor/Operations.kt::insertPageRequiresThreeDbInserts` does four inserts (page row, title block, body block, love letter). The name is stale.
- `MainPages/ViewPage/EditableBlock.kt::onValueChange` (on-screen newline): the new text contains a newline and `newValue.selection` sits after it. The code strips the newline but passes that cursor unadjusted to `onEnter`, which splits the old text. Enter in the middle of a block therefore splits one character too far right (more for a multi-line paste). At the end of the block `coerceAtMost` hides it. Hardware Enter goes through `onPreviewKeyEvent` with the real cursor and is correct, and e2e uses `KEYCODE_ENTER`, so this path is untested. Whether a given keyboard sends Enter as a key event or as text varies. From reading; not run. Fix: subtract the number of removed newlines that sit before the cursor.
- `EditableBlock::BlockActionMenu` on the title: `canMoveDown = index < session.rows.size - 1` is true for the title (index 0) but `PageSession.onMoveDown` returns for a title, so "Down" is enabled, does nothing and closes the dialog. `canMoveUp` (`index >= 2`) and `canDelete` are right. Use `!isTitle && index < size - 1`.
- Focus and scroll: the scroll to a focused row is `listState.animateScrollToItem(index)` inside each block's own `LaunchedEffect`; `ViewPage` has no page-level effect (older docs said it did). The effect only exists for a composed block, so a new row that lands below the visible area may not be composed, and then neither the scroll nor the focus happens until the user scrolls. After six failed `requestFocus` attempts it gives up without clearing `pendingFocus`. From reading; not run.
- `DbManager.hardDeletePage` removes the page, its blocks and its backlinks but not its `client_love_letter` rows, and takes no `WriteLock`. Every scratch page made by `OpsChecks` leaves letters that target a page that no longer exists (`createNewPage` always leaves an EditBlock letter, `disableHidesFromMenu` a DisablePage letter), so a second manual "Run all checks" on a real database probably fails `outbox.integrity` ("sketch target page ... not found in pages table"). Under e2e the rollback hides it. The doc comment on `hardDeletePage` also says the dev page's "Wipe all page data" uses it; that action deletes rows from four tables directly (`Tests/Actions.kt`) and never calls it. From reading; not run.
- External transaction mode (`DbManager.externalTransactionActive`): `withTransaction` runs the block inside the open transaction and has no savepoint. A block that throws returns a failure, but its earlier writes stay in the transaction until teardown, and `onRollback` (the log-buffer flush) never runs. In production the same failure rolls back. So the e2e run never exercises the rollback path, and a failed batch under e2e leaves half-applied rows.
- DB work runs on the main thread. `DbManager` has no `withContext(Dispatchers.IO)` and the uniffi calls block, so each call runs on its caller's thread. `NavPage`'s scope and `ViewPage`'s load effect are on Main, so `getMenuPages`, page create, rename and disable (yrs and the builders included) and page load all run on the UI thread; only `PageBatcher` and the dev checks use IO. The cost grows with the number of pages and blob sizes. Not measured; `ThreadUtils.kt` (`doInBackground`) not read.
- `DbManager.init` assigns `db` before it runs the migrations, and `executeNative` / `withTransaction` check only `db != null`, not `readyDeferred`. Callers that skip `awaitReady()` (the `actions`, `Logger`) can therefore run against a half-migrated database. `MigrationManager` calls `db.beginAllOrNothing()` directly, outside `dbMutex`. UI entry points do call `awaitReady()`. If `migrate` throws, `db` stays set and `readyDeferred` never completes.
- `ViewPage` load versus flush: the load effect builds the new boss from the DB without waiting for the previous session's `onDispose` flush, which runs asynchronously on the batcher's own scope. If a page is recreated inside that window (activity recreation), the new boss can be built from a blob that lacks the last edits, and later writes from it would then overwrite them. From reading; not run.
- `actions/PageActions.renamePage` always sends `Replace`, so the known non-ASCII `Delete`/`Replace` miscount in yrs (`SHARED_MEMORY.md`) applies to it: renaming a page whose current title contains å/ä/ö or emoji probably ends in "Rename failed: rename readback mismatch" and a rolled-back transaction, not a rename (the readback check stops it corrupting data). Creating such a page is unaffected (insert at 0). Typed edits that produce Delete/Replace diffs in text with such characters are exposed too, and the Kotlin block-edit path has no readback. From reading; not run; the Rust side not checked.
- `actions/PageActions.kt::createNewPage` then runs `editBlockRequiresThreeDbInserts` on the fresh boss, so a new page emits two love letters (CreateNewPage and EditBlock). Web emits one. Not a bug; noted for a future alignment pass.
- `actions/MoveBlock.kt::moveBlockToAnotherPage` doc says "neither boss has queued writes". Queues live in `PageBatcher`, not the boss, so that cannot be checked. The real requirement is "both pages' batchers are flushed". Take a session/batcher handle and flush inside, or fix the comment. An empty queue does not mean flushed: `PageBatcher.runOneFlush` drains the queue before it takes `WriteLock`, so a batch can be off the queue and not yet written while a move holds the lock. `flushNow` closes that gap because it waits on the batcher's flush mutex, but it must be called before taking `WriteLock`, since the flush takes `WriteLock` too and it is not re-entrant.
- `editor/PageBatcher` creates its own `CoroutineScope(Dispatchers.IO + SupervisorJob())` that is never cancelled. One per opened page; harmless in size but never released.
- `editor/PageBatcher.closeAndFlush` is `flushNow` and closes nothing, so the name is wrong. Rename it `flush`, or give the batcher a real close that cancels the scope and refuses later pushes.
- `editor/PageBatcher` failure path: the batch is drained from the queue before the write, so a failed batch is dropped and the page reloads from the DB. Edits pushed to the old batcher after that drain stay queued there, and its debounce can fire later against the destroyed boss. That would show a second "Save failed" popup and call `onFailed` again, bumping the shared `reloadToken` and reloading the new session. From reading only; not run. Cancel the old batcher's scope when the session is replaced.
- `editor/PageBatcher.runOneFlush` calls `GlobalPopupManager.showError` (suspend, unbuffered flow) while holding `flushMutex`, and calls `onFailed()` only after it returns. `showError` returns at once when nobody is collecting (the flow drops the value, see the `GlobalPopup.kt` entry), so recovery still runs, only without the popup. (An earlier version of this entry said recovery would hang and later flushes would wait on the mutex; that was wrong.)
- `editor/PageBatcher.debounceJob` is a plain `var` written from the main thread (`armDebounce`), from the debounce coroutine (it sets it to null) and from `flushNow`, with no lock. I found no way for it to lose data (a missed cancel flushes an empty queue), only to flush at an odd time.
- `db/migrations/SchemaVersion`: every `updateOnce` step swallows its exceptions, and `MigrationManager` records the new version regardless.
  - V0 wraps `copyTable` and `dropTable` of `uncommitted_diffs` in one try/catch, so a failed copy skips the drop and nothing is destroyed (an earlier version of this list said it dropped anyway; that was wrong).
  - V1's repair wraps its copy/create the same way, so a failed repair is written to `key_value_storage` as success.
  - V0 also drops and recreates `key_value_storage` and copies rows back only if the read succeeded. A failed read is swallowed to null and every stored row is lost, `user_id` included. Whether `XEqualY("1", "1")` returns all rows depends on z_db and was not checked.
  - V0 is ancient; this matters only if someone reseeds a V0 fixture.
- `SchemaVersion.V2.updateOnce` (V2 to V3) drops `every_block_in_existence` and recreates it empty, but leaves `pages` and their blobs alone. The nav menu is built from the mirror (`Reads.getMenuPages`), so on a device that has data every existing page disappears from the menu while its blob and outbox rows stay, and `MirrorVsYrsCheck` flags every page. Accepted as pre-data (see `OUTSIDE_ANDROID_APP.md`); a rebuild-mirror-from-blobs step would make it safe.
- `db/migrations/MigrationManager.readCurrentVersion` reads the value with `row.cols.lastOrNull()`, and its `catch (e: Exception)` returns null for any failure, not only "table doesn't exist". `migrate` treats null as a fresh database and bootstraps LATEST, so a read error on a populated database would run the bootstrap against it (what that does to existing tables was not checked). Look the key up by column name and treat only a missing table or row as fresh.
- `db/migrations/MigrationManager.migrate`: if `updateOnce` returns the same version, the loop breaks silently, `writeVersion` records that old version, and the app runs on an old schema with no error. Throw instead.
- `components/GlobalPopup.kt`:
  - `MutableSharedFlow<Popup>()` has no replay and no buffer, and with no subscriber `emit` returns at once and the value is dropped. A popup requested before `GlobalPopup()` first composes, or while the activity is being recreated, is lost without a trace (Logcat has it in debug). (An earlier version of this entry said `show` / `showError` hang until the host collects; that was wrong.)
  - `collectLatest` with `SnackbarDuration.Indefinite` means two back-to-back errors show only the second.
  - Info popups use `errorContainer` colours; only the "ERROR: " prefix differs.
  - Logcat lines are written only when `BuildConfig.DEBUG`.
- `MainPages/ViewPage/ViewPage.kt`: on load, an empty `rows` shows "Reload to try recovery" but there is no reload button. The user has to back out and reopen.
- `MainPages/ViewPage/ViewPage.kt`: `StorageAccess.setValue(StorageKey.CURRENT_DOCUMENT, pageId)` runs at the top of the load `LaunchedEffect`, outside the try/catch. If it throws, the exception escapes the effect (probably a crash) and `isLoading` is never cleared. It is a DB write in a transaction on every page open for a value nothing seen reads. Drop it (see the `CURRENT_DOCUMENT` entry below).
- `MainPages/ViewPage/ViewPage.kt` ignores the `Result` of `closeAndFlush`. If the flush fails while leaving, `PageBatcher` shows "Save failed: ... Reloading page." and bumps `reloadToken`, but the page is already gone, so the popup is misleading and the batch is lost. (An earlier version of this entry said `closeAndFlush` closes the batcher and that edits after ON_STOP would go to a closed batcher. That was wrong: `closeAndFlush` is just `flushNow`.) Nothing destroys the page's `BossOfYrs` when the page is left; only a reload does. `onDispose` still needs the boss for its async flush, so destroy it after that flush completes. Whether the uniffi object has a Cleaner was not checked (`my_yrs_lib.kt`).
- `editor/PageSession.onDeleteBlock` returns silently for the title and for the only body block. The block menu's Del button is disabled in both cases (`canDelete`), so the user sees a greyed button, not a silent no-op. (An earlier version of this entry said Del did nothing without feedback; that was wrong.) The same guard exists twice (menu and session), and `OpsChecks.deleteRules` calls the session method directly.
- `MainPages/NewPagePopup.kt`: `LocalView.current` is read in the function body, outside `Dialog { }`, so `view.parent` is the activity's content view and not a `DialogWindowProvider`. The `as?` cast yields null, and by reading the code the `SOFT_INPUT_STATE_VISIBLE` fix never runs; only the delayed `requestFocus()` and `keyboardController?.show()` do any work. Not run on a device. Move the `LocalView` read and the window tweak inside the `Dialog` content. Also `onConfirm(pageName)` passes the name untrimmed.
- Errors raised while a dialog is open cannot be seen. `GlobalPopup` is a snackbar and renders behind `Dialog` windows (`OUTSIDE_ANDROID_APP.md`). `NavPage` closes the New Page, Rename and Delete dialogs only on success, so on failure the user sees a dialog that does not close and nothing else. In debug the text is in logcat; in release it is nowhere. Show the error inside the dialog.
- `MainPages/NavPage.kt`: the Create, Rename and Delete confirm buttons have no in-flight guard, so a double tap on Create starts two `createNewPage` calls (serialised by `WriteLock`, but both run) and makes two pages. `NavPage` passes the New Page name untrimmed (Rename trims). From reading; not run.
- `MainPages/NavPage.kt` scroll-to-newest is timing-dependent. `scrollToNewest` is set before `refreshPages()` returns, so `LaunchedEffect(pages.size, scrollToNewest)` first animates to the last item of the old list and then clears the flag. If that finishes before the refreshed list arrives, the new page is never scrolled to; if the refresh arrives first, the effect restarts and works. For Rename it scrolls to the last row, not the renamed one. `refreshPages` also sets `isLoading = true`, which swaps the whole `LazyColumn` for a spinner, so the effect may be asked to scroll a list that is not composed at that moment. It also assumes the new page is last, but `getMenuPages` has no ORDER BY and `NavPage` does not sort. The e2e `create_page` leans on this with a 3 s wait. From reading; not run.

## Positional column reads (docs claim there are none)

These read by column position and would silently misread after a schema change:

- `Storage/StorageAccess.rummage_in_storage`: `row.cols.lastOrNull()`. `KeyValueStorageTableSchema.value` exists and should be used.
- `db/migrations/MigrationManager.readCurrentVersion`: same pattern.
- `DbManager.updatePageSnapshot` reads the full `pages` row and takes column 0 as the internal id (no caller seen in the files read; not grepped). `deleteRowsByColumn` requests only `id`, so its `firstOrNull` is safe.
- `SchemaVersion.V0.updateOnce`: `cols.getOrNull(0)` / `getOrNull(1)` (acceptable: frozen history).
- `Tests/CheckIfTablesInSync.checkPageSync`: reads the page blob at `pageRow.cols.getOrNull(2)` by position. The block id and content columns are found by name through `checkTable`, but a -1 from `indexOfFirst` is not handled (`getOrNull(-1)` is null, so every row maps to the key "" and they collapse into one).
- `Tests/MirrorVsYrsCheck` (`pageIdIdx = 1`) and `Tests/OutboxIntegrityCheck` / `OutboxReplayCheck` (`cols.getOrNull(1)`) all read `page_id` from `getPages()` rows by position. The two outbox checks also index `love_letter_sketch`, `snapshot_of_edit` and `id` by position in their own `columnsToRead` lists, which is consistent only if the read returns columns in the requested order. A `getAllPageIds()` in `Reads.kt` would remove the first three.
- `InspectTable.kt`: delete reads `row.cols.firstOrNull()` as the id. (Insert is by column name, so column order does not matter.)
- `TestTransactionReceiver` (CHECK_SYNC branch): the title-to-pageId lookup finds the column indexes by name through `checkTable`, but filters `is_title` in Kotlin and takes `firstOrNull`, so two pages with the same title resolve to whichever row comes first. The `?: 1` / `?: 5` fallbacks only fire when `checkTable` itself fails, not when `indexOfFirst` returns -1 (then `getOrNull(-1)` is null, nothing matches, and the raw title is used as the page id).

- `SchemaGui.kt` hardcodes five tables. `logs` and `incoming_love_letters` are missing. Drive the list from `DbManager.listTables()` plus `checkTable`.
- `Tests/DevToolsPage.kt`: a check card's `onClick` runs the check when nothing is running and toggles the detail only while a run is in progress. ## Different shape from web, not necessarily wrong

Called out so nobody "fixes" them into breaking:

- `PageBatcher` on Android is one class with its own debounce timer, mutex and queue. Web has a `BatcherHandle` plus a run-loop task.
- `DbManager` uses `DbTransactionElement` in the coroutine context for re-entrancy. Web uses `WriteLock` + `run_exclusive`.
- Android batches Delete and Move in the same queue as Edit and Add (see `INVENTED_ON_ANDROID.md`).
