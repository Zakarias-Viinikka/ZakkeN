## How I want the code to be structured

The drag UI is a thing you call, not a thing you own. From the outside it looks like any other component: you hand it pages, blocks, and a callback that fires when something moves. It does not get a database handle, a yrs doc, a websocket, or anything else about the caller's project. It does not know what a page is beyond "a thing that has an id and holds blocks", and it does not know what a block is beyond "a thing that has an id, belongs to a page, and has content you can type in."

State lives with the caller. The caller loads pages and blocks from wherever they come from and gives them to the component as plain data. The component renders them and, when the user drags a block, figures out where it ended up and calls back with a description of the move: which block moved, which page it came from, which page it went to, and which block is now directly above and below it in the destination. That is the whole contract. The cascade, the rapier world, the vacuum, the confirmation lines, the height tracking — all inside the component, none of it visible to the caller.

It is a callback and not a return value because drags happen asynchronously and there is no "the drop finished, here is your answer" moment to await. The component runs the animation, updates its internal arrangement so the UI feels right, and then tells the caller what happened. The caller does whatever the app needs with that description — write it to the db, send it to a server, update its own state — and if the result differs from what the component is showing, the component notices on the next render and corrects itself. That is the sync path: feed it state, it tells you when state changed, you feed it new state.

The point of the clean boundary is that the component can drop into any project. As long as the caller can produce a list of pages and a list of blocks and has somewhere to put a callback, the component works. It has no opinion about storage, sync, or networking. It draws a page, moves blocks around, and tells you when they move.

The input types are plain strings for ids and content, nothing else. No newtypes, no enums, no serde, no wrapper structs. The caller's types should be whatever the caller already has — a db row, a network payload, whatever. Making the component demand a specific shape forces translation, and translation is where bugs live. Plain strings means zero friction to feed it and zero friction to reuse it. The only thing the component adds is meaning: these two ids are the same thing, this block belongs on this page, this is the order top to bottom.

`on_move` carries above and below rather than a raw position number because positions are an implementation detail the caller should not have to reconstruct. A position index forces the caller to look up its own list, find what is at index-1 and index+1, and make sure its list agrees with the component's. Above and below as ids lets the caller write the same db update it would write for any "insert between these two things" operation, and it works the same whether the block moved one slot or fifty. The component has already figured out what the final order is, so it reports that, not raw drop coordinates.

The move event fires on every completed drop onto a page, including a drop into the same slot. That is deliberate: the caller does not have to compare old and new state to decide whether to write. It just gets told "a drop happened, here is what it meant" and always writes. If the caller's app is smart enough to detect a no-op, that is the caller's business; the component is honest about what happened. It also fires when a block is restored from the vacuum onto a page, because from the caller's point of view that is a move — the block went from somewhere to a page. It does not fire for a click without movement, for a drag released outside every page, or for a block dropped into the vacuum, because none of those are moves from the caller's perspective: nothing changed about which page holds which block.

The ghost model is what makes the vacuum work cleanly. Vacuuming a block does not remove it from the layout. It stays where it was, rendered as a dashed empty box, and blocks below it still treat it as occupying space. Vacuuming therefore does not cause a cascade. When the block is later dropped back onto a page, the ghost is what the callback fires against: the block "moved" from the page its ghost sat on to wherever it landed. If a second block is vacuumed while one is already vacuumed, the first comes back to its own slot, because its ghost is still there and the ghost just becomes real again. From the caller's point of view, nothing about the vacuum needs to be modeled — no "vacuumed" flag on the caller's block, no separate list of vacuumed things. The component handles all of it internally.

Heights are live. Blocks grow and shrink as the user types, and the blocks below them follow. That is true even while a cascade is running. Heights come from the DOM, not from the caller, because the caller should not have to measure text to feed the component the right height. The component watches each block's rendered size and pushes changes through the same commit path any other layout change goes through. If the caller later wants to know a block's height — to save it, or reason about layout — that is a future feature. For now the height is a fact the component owns.

The prop signals are signals rather than plain values because real projects load asynchronously. A `Vec` could not react to "the data just arrived" or "the user made a change and now the list is different." Signals let the component watch for changes and reconcile, and let the caller be as lazy or eager as it wants. The contract: whenever the signals change, the component compares the new shape to what it is currently showing; if they match, it does nothing; if they do not, it adopts the new shape. The caller can re-send the same data on every render and the component will ignore it, or the caller can push a change and the component will follow.

The single-page mode is a test, not a feature. The geometry already supports arbitrary N pages, and flipping between one and two pages at runtime exercises the "signals changed, reconcile" path. Without something forcing the prop signal to actually change, the sync code would never run and nobody would know if it worked. It is the smallest possible proof that the boundary works both ways: the component can render what you give it, and you can give it something different and it adapts.

The reason all of this matters is that you want to be able to change the surrounding project without touching the component. If the db schema changes, the component does not care. If the sync story changes, the component does not care. If you add undo, persistence, history, or a server, none of those touch the component — they touch the caller, because the caller owns state and the component owns presentation. The component is a leaf. It sits at the bottom of the tree and only knows about the pixels it is drawing and the drags the user is doing on them. Everything above it is yours, and it does not want to know.
